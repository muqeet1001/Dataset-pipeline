2. THE COMPLETE REQUIRED FLOW

One program invocation must perform, per dataset record:
  read measurements and source metadata
  -> generate or resume the verified MHR body
  -> load that body into a browser simulation worker
  -> select a shirt and pants from the matching male/female catalog
  -> position the outfit on the body
  -> simulate tight, medium and loose variants
  -> validate and export the three results and metadata
  -> persist a durable handoff for the next stage
  -> move to the next record.

Use the same shirt style, pants style and fabric definitions across the three
variants for that subject. Choose styles with a recorded seed; persist the
selection so a resume does not randomly change the outfit.

For each record the input can be just the generated avatar and its existing
metadata. Clothing assets, fit profiles, placement rules and fabric settings are
prepared once and stored with the application. There must be no per-record file
upload, manual garment placement, terminal command or button clicking.

Also provide an interactive local preview where I can load a supported avatar,
see the outfit, switch tight/medium/loose, simulate/reset and download results.
For a standalone avatar, request explicit units/sex metadata when unknown or use
an explicitly unisex template; do not infer sex from body appearance. The dataset
batch already supplies its recorded sex through source-record.json.

3. TECHNOLOGY AND SCOPE

All clothing simulation must execute inside the browser runtime, with Three.js
for the 3D scene. A JavaScript/WebAssembly cloth solver or custom browser solver
is acceptable. WebGPU may accelerate it when actually supported. Inspect browser
and hardware capabilities; provide a working CPU/browser alternative or a clear
unsupported-runtime failure rather than silently disabling physics.

Do not require VStitcher, CLO or Blender for the per-subject clothing simulation.
Ordinary one-time asset conversion is fine. Keep the run local on existing EC2.
Use maintained, suitable dependencies where available, pin their versions and
record third-party code/asset provenance and licenses. A general rigid-body engine
wrapper alone is not a complete garment solver.

Do not implement video generation, animation sequences, Unreal, model training,
deployment services, or other later pipeline stages. Diagnostic screenshots are
part of validation, not a new synthetic-video stage.

4. CLOTHING ASSETS AND PLACEMENT

Start with a simple short-sleeve shirt and long pants. Obtain suitable reusable
assets, or implement clearly identified procedural sewing/pattern templates if
available assets cannot be adapted. Real sources to inspect:
  https://static.makehumancommunity.org/assets/assetpacks/shirts01.html
  https://static.makehumancommunity.org/assets/assetpacks/pants01.html
Those particular packs list CC0 assets; preserve the individual provenance.
MakeHuman's automatic clothing mappings refer to its own basemesh, so adapting
them to MHR requires a fitting/mapping step. Do not assume they fit MHR directly.

Keep garment templates, rest dimensions, seams, openings, fabric properties and
placement landmarks explicit. A generic GLB's appearance materials do not supply
all the cloth simulation parameters we need. Do not invent measured fabric data;
label chosen presets as assumptions until calibrated.

Enrol male and female garment/outfit pools. Keep this browser catalog separate
from the old native VStitcher size-ID schema. Do not fabricate native size IDs
for browser templates. If only one eligible style is available in a pool, report
that limited diversity honestly.

Keep the MHR body immutable. Locate neck, shoulders, armpits, waist, hips, crotch
and limbs from suitable transformed MHR data and/or validated mesh landmarks.
Align shirt neck/sleeves and pants waistband/legs. Start from a sensible pose
with low initial penetration, correct orientation and open garment openings.
Handle the waistband/support with documented seam/elastic/constraint behavior.
Avoid pinning whole garments to the skin just to conceal placement failures.

5. REAL BROWSER PHYSICS

Implement or integrate a cloth-capable solver, for example a position-based
constraint approach with a fixed timestep and bounded substeps/iterations.
Required behavior includes gravity, mass/damping, stretch/shear/bending behavior,
body collisions, cloth self-collision and interactions between shirt and pants.
Use suitable collision thickness and friction. A wavy shader, baked animation,
vertex offset or pure shrinkwrap is not the requested cloth simulation.

Use explicit units: source MHR PLY is in centimetres. If simulating in metres,
convert through a recorded transform and validate the inverse/roundtrip. Record
export units, especially for GLB. Do not change the underlying body's dimensions.

Body collision must meaningfully represent the MHR surface. Approximate colliders
may help a coarse stage, but final validation must check against the actual body.
Use acceleration structures as needed. Do not hide body regions or move the body
to conceal garment intersections. Do not promise collision-free simulation merely
because collision settings are enabled.

Run until a documented settling criterion is met or a bounded work/time limit is
reached. Record the criterion, timestep, iterations/substeps, convergence metrics
and errors. Unsettled, unstable or invalid results must fail or remain pending.
Use bounded retries with recorded changes; preserve the original failed attempt.

Useful starting points, not complete avatar dressing implementations:
  https://threejs.org/examples/webgpu_compute_cloth.html

  https://threejs.org/examples/physics_ammo_cloth.html

6. TIGHT, MEDIUM AND LOOSE

Create three garment rest-size/pattern variants around the SAME body. Change
documented garment dimensions/ease, rather than scaling the body, changing only
collision clearance, or changing fabric stiffness to manufacture fit labels.
Use meaningful grading across torso, sleeves, waistband, hips and legs. If using
parametric patterns, save their parameters and measured rest dimensions.

The old prototype bands (tight 0-6%, medium 6-14%, loose 14-30% primary-circumference
ease) are only initial operational targets. They are not universal physical-fit
criteria and do not validate pants/other dimensions. Choose and document suitable
profiles; calibrate on actual results. Do not introduce negative ease without
appropriate stretch behavior and validation.

The labels initially mean intended fit. Save checks for the observed fit, strain,
clearance, penetration and convergence separately. An attractive render or three
different garment sizes does not by itself prove physically correct fitting.
